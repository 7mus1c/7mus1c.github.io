## RAG架构是什么样的

**离线索引**：数据源 → 文档解析与清洗 → 文本切片 Chunking → 元数据构建 → Embedding 向量化 → 索引构建与持久化

1. 数据源：PDF、Word、网页、Markdown、数据库、业务系统
2. 文档解析与清洗：正文提取、OCR、表格解析、去噪、结构识别
3. 文本切片 Chunking：按语义或标题切分、控制长度、设置重叠
4. 元数据构建：文档 ID、标题、来源、页码、时间、权限
5. Embedding 向量化：将文档片段转换为向量表示
6. 索引构建与持久化：向量索引、关键词索引、原文片段、元数据（保存原文和元数据，生成并保存向量，同时建立能够快速搜索这些数据的索引）

**在线问答**：用户输入 → Query 预处理（可选） → 检索 Retrieval → 融合与重排序 → 上下文组装 Context Assembly → Prompt 构建与 LLM 生成 → 答案后处理与返回

1. 用户输入 Query：接收问题、用户身份与会话上下文
2. Query 预处理（可选）：问题改写、查询扩展、意图识别
3. 检索 Retrieval：查询向量化 + 向量检索；可结合 BM25 混合检索、权限过滤
4. 融合与重排序：合并检索结果、去重、Rerank、Top-K 筛选
5. 上下文组装 Context Assembly：拼接相关片段、来源信息，控制上下文长度
6. Prompt 构建与 LLM 生成：注入用户问题、检索证据和回答规则
7. 答案后处理与返回：来源引用、格式化、必要的拒答与安全检查

## RAG 的核心技术组件

| 组件             | 主要职责             | 常见技术选型             |
| ---------------- | -------------------- | ------------------------ |
| 文档解析         | 读取不同格式的文档   | Unstructured、PyMuPDF    |
| 文本切片         | 划分文档片段         | LangChain Text Splitters |
| Embedding 模型   | 文本转向量           | BGE、Qwen Embedding      |
| 向量数据库       | 存储和检索向量       | Milvus、Qdrant、pgvector |
| 检索器 Retriever | 查找相关片段         | 向量检索、BM25、混合检索 |
| 重排序 Reranker  | 对检索结果重新评分   | BGE Reranker 等          |
| 大语言模型 LLM   | 理解上下文并生成答案 | GPT、Qwen、DeepSeek 等   |
| 编排层           | 串联整个问答流程     | LangChain、LlamaIndex    |

这些技术并不需要全部使用。比如，小型项目可以用 PostgreSQL + pgvector + 一个 Embedding 模型 + 一个 LLM 搭建基础 RAG。

## 向量数据库的原理

向量数据库（Vector Database）的核心原理，可以理解为：**把文字、图片、音频等数据转换成一串数字（向量），再通过计算向量之间的相似度，快速找到语义上最接近的内容。**

### 向量到底是什么？

向量本质上就是一个数字数组。

例如，假设某个模型把文本映射成三个维度（仅用于演示，实际模型通常有数百到数千维）：

**注意：不管多少个字最后向量的维度都是一样的。**

| 文本           | 示例向量             |
| -------------- | -------------------- |
| 苹果是一种水果 | `[0.9, 0.2, 0.1]`    |
| 香蕉是一种水果 | `[0.85, 0.25, 0.12]` |
| 汽车可以行驶   | `[0.1, 0.8, 0.9]`    |

前两句话的向量比较接近，第三句话则相距较远。

### 如何衡量向量相似度？

常见方法有三种：

- 余弦相似度（Cosine Similarity）：比较两个向量的方向，是语义检索中常见的选择。
- 欧氏距离（L2 Distance）：计算两个向量在空间中的直线距离。
- 点积（Dot Product）：计算向量对应维度乘积之和，具体效果取决于模型和向量是否归一化。



归一化：把数据按照一定规则进行缩放或转换，让它变得更容易比较、计算。

### 向量数据库如何实现快速检索？

假设你有 1 亿条向量数据。如果每次查询都逐条计算相似度，就需要比较 1 亿次，开销可能非常大。

因此，向量数据库会使用索引和近似最近邻搜索（ANN，Approximate Nearest Neighbor）技术。

**ANN 索引三大流派**

| 索引                         | 思路                                                         | 优点                     | 缺点                   |
| :--------------------------- | :----------------------------------------------------------- | :----------------------- | :--------------------- |
| **HNSW**（分层可导航小世界） | 将向量组织成多层图结构。查询时先在高层快速定位，再逐层深入，寻找附近的候选向量。它是很多向量数据库常用的索引方案。 | 查询快、召回高           | 内存占用大、构建慢     |
| **IVF**（倒排文件 / 聚类）   | 先将向量聚类成多个区域。查询时只搜索部分相关区域，而不是遍历全部数据，适合某些大规模检索场景。 | 省内存、易扩展           | 召回略低（边界点易漏） |
| **PQ**（乘积量化）           | 将向量压缩成更紧凑的编码，降低内存占用和计算成本，常与其他索引组合使用。 | 极致省内存（4~64× 压缩） | 有精度损失             |

实际产品常**组合**使用，例如 `IVF + PQ`（省内存）+ `HNSW`（快），用精度换吞吐/成本。

### 常见的向量数据库有哪些？

| 名称     | 特点                                                         |
| -------- | ------------------------------------------------------------ |
| Milvus   | 开源向量数据库，面向大规模向量检索                           |
| Qdrant   | 支持向量检索和丰富的元数据过滤                               |
| Weaviate | 提供向量检索及相关数据管理能力                               |
| Pinecone | 托管式向量数据库服务                                         |
| FAISS    | Facebook AI Research 开发的向量检索库，本身不是完整的数据库服务 |
| pgvector | PostgreSQL 的向量扩展，适合在关系型数据库中加入向量检索      |

## 数据是怎么转换成向量的

**不是把文字直接转换成数字，而是通过一个训练好的 AI 模型，把文字的语义编码成一串数字。**

1. **原始文本**：“我喜欢吃苹果”
2. **分词（Tokenization）**：将文本切分成模型能处理的 Token，`我` `喜欢` `吃` `苹果`
3. **Token 编码与初始向量**：Token ID 查表，转换成数字向量，[102, 305, 87, 920]
4. **神经网络处理**：Transformer 等网络结合上下文，提取语义特征
5. **汇总成一个向量**：Pooling 等操作，将多个 Token 的表示合并，[0.23, -0.61, 0.48, ...]
6. **最终 Embedding**：例如一个 1536 维的向量

## 向量维度

**Embedding 向量维度越多，不代表效果一定越好。** 维度只是向量包含多少个数字，不直接代表模型的理解能力。真正重要的是模型能否把你需要的相关文档排在前面，以及检索成本是否合理。

当然维度越多，它的召回率更好（越精准）。但是存储空间占用更多。

**主流向量维度**

| 模型                            | 默认向量维度 | 特点                           |
| ------------------------------- | ------------ | ------------------------------ |
| OpenAI `text-embedding-3-small` | 1,536        | 通用场景，成本较低             |
| OpenAI `text-embedding-3-large` | 3,072        | 更强调检索质量，可调整输出维度 |
| BAAI `bge-m3`                   | 1,024        | 多语言、长文本检索             |
| BAAI `bge-large-zh-v1.5`        | 1,024        | 中文语义检索                   |
| `multilingual-e5-large`         | 1,024        | 多语言检索                     |
| `all-MiniLM-L6-v2`              | 384          | 轻量模型，常用于英文语义搜索   |
| `nomic-embed-text-v1.5`         | 768          | 支持可调维度的向量表示         |

## 长文档向量化

一本 10 万字的书，不是直接一次性转换成一个向量，而是通常要先把书切分成很多小段，再分别进行 Embedding 向量化，最后存入向量数据库。

1. 提取文本
2. 文本切片（Chunking）
3. 批量调用 Embedding 模型
4. 存入向量数据库
5. 用户提问时检索相关片段

### 10 万字大约会生成多少个向量？

假设这本书有 100,000 个中文字符：

比如，每段 800 字，相邻重叠 100 字，每次实际向前推进 700 字，那么 10 万字大约生成 143 个向量。

**“相邻重叠”就是：切分文本时，让前后两个片段共享一部分相同的文字，避免一句话或一个知识点刚好被切断。**

```shell
片段 1
今天我们来学习向量数据库。它可以把文本转换为向量，并根据语义相似度查找相关内容。接下来介绍文本切片……


两个片段共同包含的文字
重叠区域：20 个字
前一个片段结尾的 20 个字，会再次出现在下一个片段的开头。

片段 2
（重复的 20 个字）……接下来介绍文本切片。合理的切片能够保留完整的语义，方便后续检索。
```



### 为什么要切片，而不是整本书生成一个向量？

假设整本书只生成一个向量：

- 用户问第 3 章的某个技术细节。
- 你只能拿到代表整本书的一个向量。
- 书里不同主题的细节被混合在一起，难以精确定位。

如果切成 143 个片段，每个片段各自生成一个向量，系统就可以只找出与问题最相关的几段。

例如：

| 向量 ID    | 章节     | 内容     |
| ---------- | -------- | -------- |
| `book_001` | 第 1 章  | 基本概念 |
| `book_002` | 第 1 章  | 核心原理 |
| `book_003` | 第 2 章  | 系统架构 |
| `book_004` | 第 2 章  | 实现细节 |
| ...        | ...      | ...      |
| `book_143` | 第 10 章 |          |

```json
{
  "id": "book_003",
  "vector": [0.12, -0.35, 0.81],
  "text": "系统架构的具体内容……",
  "metadata": {
    "book_id": "book_001",
    "chapter": "第2章",
    "chunk_index": 3
  }
}
```

### 如何切片效果最好？

建议不要简单地每 800 个字符机械切断，而是优先利用书本自身的结构。

1. **先按章节切分**：识别书名、章节标题、小节标题，尽量不要让一个片段跨越两个完全不同的主题。

2. **再按段落切分**：把相关段落组合成适当长度的片段。技术书中的公式、代码和定义应尽量保持完整。

3. **保留适量重叠**：例如相邻片段重叠 50～150 个字符，避免重要定义恰好被切断。并非所有文档都必须重叠。

4. **保存元数据**：为每个片段保存书名、章节、页码、片段编号，方便检索后定位原文和引用来源。

## 业内一般切片多大？

| 场景              | chunk 大小       | overlap | 说明                             |
| :---------------- | :--------------- | :------ | :------------------------------- |
| 通用文本 RAG      | 256–512 token    | 10–20%  | 最主流区间（如 256+64、512+128） |
| 短事实问答 / FAQ  | 128–256 token    | 10%     | 信号集中，检索最锐               |
| 长文总结 / 章节级 | 512–1024 token   | 15–20%  | 保上下文，问"总结第X章"更稳      |
| 代码              | 512–1024 行/字符 | 15%     | 函数/类为界                      |
| LlamaIndex 默认   | ~1024            | 20%     | 偏保守，常需下调                 |
| LangChain 默认    | 1000 字符        | 200     | 偏宽松，常需下调                 |

**核心原则：切片粒度 = 你预期问题的粒度。** 

## 如何平衡分块大小与检索精度？

本质矛盾：**块太小会丢失语义；块太大则容易混入噪音。**。

1. **父子块**
   - 子块 200–400 字做向量检索，父块（章/节）存原文。
   - 命中子块 → 用 parent id 取父块 → 父块原文喂 LLM（上下文全）。
2. **句窗检索（Sentence-Window）**
   - 索引到句子级，召回后把该句 + 上下 N 句窗口一起给 LLM。比父子块更细。
3. **小块 + 富元数据**
   - 小块（256）配 书名/章/节/页码 元数据。即使块很小，LLM 也能从元数据知道出处，且可用元数据过滤（"只看第 3 章"）。
4. **小块检索 + 混合 + 重排**
   - 小块（256）做向量召回 → BM25 补字面匹配（短关键词超有用）→ Reranker 精排 top-5。
   - 这是当前生产环境精度上限最高的组合。

## **如何处理短且离散的QA对或者短句列表**

**一个离散单元 = 一个 chunk，绝不把多条并成一大块**

**场景 A：FAQ 问答对**

推荐：一问一答作为一个独立索引单元。

原始数据：

- Q：如何重置密码？
- A：进入账号设置，点击重置密码并完成邮箱验证。

建议用于 Embedding 的文本：

`问题：如何重置密码？答案：进入账号设置，点击重置密码并完成邮箱验证。`

不要只对答案向量化，否则用户用“密码忘了怎么办”这类不同措辞提问时，可能不容易匹配。

**场景 B：独立短句列表**

推荐：每条短句独立向量化，并保留来源信息。

例如：

- HNSW 是一种基于分层图的近似最近邻索引。
- BM25 是一种基于词项统计的相关性排序方法。
- L2 归一化会将非零向量缩放为单位长度。

这三条属于不同知识点，应该分别建立向量，而不是合成一个 Chunk。

**场景 C：同一主题下的多个短句**

推荐：独立索引，必要时增加主题上下文。

如果多条短句都来自“HNSW 参数配置”这个主题，可以在每条记录中增加主题字段或上下文前缀，但仍然保留独立 ID。

这样既能单独命中具体参数，又能通过主题过滤或聚合找到相关知识。

### 短 QA 的最佳实践：同时保存检索文本和原始答案

建议每条 QA 记录包含以下字段：

| 字段             | 用途                 |
| ---------------- | -------------------- |
| `id`             | 唯一标识             |
| `question`       | 原始问题             |
| `answer`         | 原始答案             |
| `embedding_text` | 用于生成向量的文本   |
| `topic`          | 主题分类             |
| `aliases`        | 同义问法、常见表达   |
| `source`         | 来源、版本或权限信息 |

例如：

```json
{
  "id": "faq_001",
  "question": "如何重置密码？",
  "answer": "进入账号设置，点击重置密码并完成邮箱验证。",
  "embedding_text": "主题：账号安全。问题：如何重置密码？答案：进入账号设置，点击重置密码并完成邮箱验证。",
  "topic": "账号安全",
  "aliases": [
    "密码忘了怎么办",
    "如何找回登录密码"
  ]
}
```
