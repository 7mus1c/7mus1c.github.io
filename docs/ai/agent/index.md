# 什么是 AI 应用？

AI 应用，就是把一个"训练好的 AI 模型"当成核心能力引擎，去完成感知、理解、生成、推理、决策这类任务的软件系统。

这个软件里"智能行为"是谁产生的？
是自己写死的规则 → 普通软件。
是模型在运行时"现想出来的" → AI 应用。

## AI 应用的三层构成

1.  **能力底座(模型)：** LLM（GPT/DeepSeek）、视觉模型、语言模型等。通常不需要自己训练，直接调用API 。
2.  **应用层(编排)：** 这是 AI 应用的核心，负责怎么把用户请求变成好的提示词（prompt），怎么接外部知识(Rag), 怎么让模型调用工具（function call/MCP），怎么处理流式输出和错误。
3.  **交互层(界面)：** 把模型的能力包装成人类能用的产品（聊天框、写作面板、Agent工作流等）。



## 主流大模型

- GPT
- Claude Code

## 总结

AI 应用 = 借一个训练好的模型当大脑，用工程 + 界面把它变成能解决具体问题的产品；你不必造大脑，但你要造好"身体"和"嘴"。
从程序员角度去看就是 Ai SDK + Java + 前端 + 运维 = AI应用。

## AI 应用目前的市场分类和技术分布

### 纯生成类

- 典型应用：写小说、写周报、陪聊、 AI 绘画。
- 核心：靠大模型原本训练好的知识。
- RAG 的作用：不大。主要是靠模型的创造力。

### 知识检索类

- 典型应用：智能客服、垂直领域问答（医疗、法律、金融等），私有数据搜索。
- 核心：大模型 + 外部数据。

### 自主行动类

- 典型应用：帮你订机票、自动写代码并运行、操作 Excel 生成图表。（ChatGPT codex/Claude code/WorkBuddy）。
- 核心：大模型 + 工具（Tools）+ 规划（planning）。

举个例子，一个订机票的 AI 应用，它需要调用机票 API、酒店 API、地图 API、天气 API 等等，这些 API 就是工具。它还需要根据用户的输入，规划出一条最优的路线，比如先订机票，再订酒店，车。这些规划就最后订是规划。

## RAG 是什么？

RAG（检索增强生成）其实是 AI 应用的架构模式，它是对 LLM 能力的增强和补充。让 LLM 在回答之前，先去「外挂知识库」里查资料，再把查到的内容作为依据来生成答案。

### RAG 的作用

LLM 天生有三个毛病，RAG 正好对症：

1. 幻觉：模型凭空编答案（因为你问的它没学过）。
2. 知识截止：GPT-4 只知道训练截止日之前的事，今天的新闻它不知道。
3. 私有数据进不去：你的公司内部文档、个人笔记，模型根本没见过。

## LLM 在 AI 应用中的角色

**读懂人话，把人话变成指令，调度 AI 应用工作，再把数据整合成人话返回给用户。**
LLM 在 AI 应用里是"理解 + 推理 + 生成 + 调度"的中枢控制器；它强在泛化，弱在事实、行动、记忆和确定性——AI 应用的工程就是用 RAG、工具/ MCP、记忆、护栏和 UI 把这几个短板逐一补上。

## 提示词的核心要素

| 核心要素 | 英文术语 | 作用（缺失时症状） | Agent 中的例子 |
| :-- | --- | --- | --- |
| 角色与目标 | Role & Goal | 明确身份与首要目标，防止回答泛泛而谈（缺失 → 语气不对、专业深度不对） | 你是一位专业的安全审计师，目标是找出合同中所有的风险条款 |
| 上下文 / 数据 | Context / Input | 提供决策所需的背景资料或 RAG 检索结果（缺失 → 答案正确但不适用） | `[Context_Data] 客户合同在这：{contract_text}` |
| 任务指令 | Task / Action | 精确指定要完成的具体动作与步骤（缺失 → 东拉西扯、答非所问） | 请根据合同内容，找出所有可能的风险条款 |
| 约束边界 | Constraint | 限制发挥空间，控制语气、风格与安全边界（缺失 → 答案不完整、超出边界） | 请使用中文回答，语气专业，不带任何感情色彩 |
| 输出格式 | Format / Schema | 规定输出结构，保证结果可被下游消费（缺失 → 格式混乱、无法解析） | 将结果输出成 Markdown，每个风险点一个 `###` 小标题 |

### 不同 LLM 之间的 Prompt 相似吗？

底层原理相似，但是格式和效果天差地别。

**Prompt 必须根据模型去做微调**。绝对不能把给 GTP 的 Prompt 直接拿给 Claude 或者 DeepSeek 直接去用。

## Function Call

### 什么是 Function calling

**Function Calling（工具调用 / Tool Use）= LLM 不直接回答，而是先输出一段结构化的「我要调用某个函数、参数是这些」的请求；由你的代码真正去执行，再把结果回灌给模型，让它据此组织最终回答。**所以简单理解 Function Call 就是让大模型拥有调用工具的能力。

例如：

```text
LLM 输出：{"想调用": "查天气", "参数": {"城市": "上海"}}
你的代码：真的去调天气 API，拿到 {"temp": 22}
```

如果没有 Function Calling 那么大模型就会胡说八道。

### 完整链路（至少两次 API 往返）

```text
① 请求：把「用户问题 + 工具清单（名称/描述/参数 Schema）」一起发给模型
        ↓
② 模型判断：需要调工具吗？调哪个？参数是什么？
        ↓
③ 响应：不返回自然语言，返回结构化 tool_calls（JSON）
        ↓
④ 你的代码：解析 JSON → 执行真实逻辑（调 API / 查库 / 算数）→ 得到结果
        ↓
⑤ 第二次请求：把结果作为一条 tool 消息，连同历史一起再发回模型
        ↓
⑥ 最终响应：模型基于结果，生成人能读的回答
```



## 什么是 MCP

AI 应用 → LLM 是决策中枢 → RAG 给它补知识 → **MCP 给它装手脚**。

**MCP（Model Context Protocol，模型上下文协议）= 一套开放标准，规定 AI 应用怎么统一地连接外部数据源和工具。**

### 没有 MCP

想要让 Agent 读取 MySQL ？得写 Python 代码用 PyMySQL 库。

想要让 Agent 链接 GitHub？得写代码调用 GitHub API。

痛点：每个数据都需要写一套”胶水代码“，无法复用。

### 有了 MCP

MySql 官方提供一个 MCP Server。

GitHub 官方提供一个 MCP Server。

Agent 只要支持 MCP 协议，不需要写一行针对 MySQL 或者 GitHub 的代码。直接插上就能读写数据。

### 三层架构

- MCP Host：承载了 AI 主程序，发起链接 例如：codex、Claude Desktop 、自己的 Agent。
- MCP Client：Host 内部的连接器，1 client 对 1 Server 例如：SDK里面的 Client 实例。
- MCP Server：把外部能力按标准暴露出来的服务 例如：GitHub 官方 MCP Server、自己包的一个查库服务。

### MCP Server 暴露的三类

- Tools（工具）：模型可调用的动作，如：发邮件、建 issue、执行 SQL 。
- Resource（资源）：可以被读取的数据，如：文件内容、数据库记录、API 返回值。
- Prompts（提示模板）：预制的 prompt 模板，如：代码审查、周报生成。

### 完整链路

```text
用户：明天上海天气如何？
  ↓
① Host 启动时连上所有 MCP Server，拿到工具清单（名称+描述+参数 schema）
② Host 把「用户问题 + 工具清单」一起塞给 LLM
③ LLM 决策：要调用 get_weather(location="上海", date="明天")
  ↓ Function Calling 输出结构化调用请求
④ MCP Client 按协议把请求发给对应 Server
⑤ Server 执行真实操作（调天气 API），返回结果
⑥ 结果回灌给 LLM，LLM 组织成自然语言回答
  ↓
用户：明天上海多云转阴，18–24℃，东南风 3 级。
```

## MCP 和 Function Call 的区别

**Function Calling 负责「决定调什么」，MCP 负责「工具怎么接进来」。** 没有 Function Calling，模型不知道要调工具；没有 MCP，你得给每个工具手写一遍适配代码。

|          | Function Calling                           | MCP                                          |
| -------- | ------------------------------------------ | -------------------------------------------- |
| 本质     | 模型的能力                                 | 接口/集成标准                                |
| 解决什么 | 让模型有输出“我要调用xxx 函数”的结构化请求 | 让工具和数据怎么被**发现、描述、连接、复用** |
| 类比     | 你的"手"（能执行动作）                     | USB-C 接口 + 驱动（怎么接上去）              |

## 向量数据库

**向量数据库 = 专门用来存「向量」并做「相似度检索」的数据库。** 它的核心能力不是"查出值等于 X 的行"，而是"**找出和这个东西最像的 Top-K 条**"。

### 为什么传统数据库不行

传统数据库是为了精确查找设计的，但是向量数据库要在一个 768 维 / 1536 维的空间里，找出离目标点最近的 K 个邻居。

那么传统数据库要在高维空间里面做距离计算量爆炸，**线性全表扫描会被拖死**。

但是向量数据库是牺牲一点点精度，换几百倍的速度。这就是向量数据库存在的根本理由。

比如：你要查找一个你今天吃了没，有些人会用方言“你今天恰饭了吗”？或者“你今天吃了某？”再或者"吃了嘛您内？"，这你让传统数据库怎么查询？

但是向量数据库会在查跟这一句最相似的几句查出来：

1. 今天吃点什么
2. 今天吃了啊
3. 今天吃没吃
4. 我今天吃了辣子鸡丁

### 为什么 RAG 需要用向量数据库

因为有些时候 LLM 的模糊搜索并不精确，所以需要精准搜索两者相结合，才能正确回复提问。而且有些时候 LLM 并没有内部数据，所以需要给 LLM 补充内部文件，数据。

## Langchain

**LangChain 是一个开源的 LLM 应用开发框架**，类似于 Java 里的 spring 前端里的 Vue、 React。

它把做 AI 应用常用的零件（接模型、prompt 模板、RAG 管线、工具调用、记忆、Agent 编排）封装成现成模块，你不用从零手搓。它就是**编排框架**。

| 开发中你要解决的问题                           | LangChain 提供的东西                             |
| :--------------------------------------------- | :----------------------------------------------- |
| 各家模型 API 格式不一                          | 统一的 Model 接口，换模型基本只改一行            |
| prompt 要拼变量、要复用                        | PromptTemplate 模板化管理                        |
| 加载 PDF/网页 → 切片 → embedding → 存库 → 检索 | 现成的 RAG 管线（Loader / Splitter / Retriever） |
| 想让 LLM 调工具并循环                          | 统一的 Tool 抽象 + Agent 执行器                  |
| 多轮对话要记上下文                             | Memory 组件                                      |
| 模型输出要变成结构化数据                       | Output Parser（JSON Schema）                     |
| 调试、评测、线上监控                           | LangSmith（配套平台）                            |

### 全家桶

| 组件          | 分工                                                         |
| :------------ | :----------------------------------------------------------- |
| **langchain** | 基础库：模型接入、prompt、retriever 等可复用零件             |
| **LangGraph** | ⭐ **当下官方主推**：用"有向图/状态机"编排 Agent 和多步工作流，适合有分支、有循环、要中断恢复的复杂逻辑 |
| **LangSmith** | 调试追踪、数据集评测、线上监控（多数团队实际离不开的一块）   |
| LangServe     | 一键把链/图发布成 HTTP 服务                                  |
